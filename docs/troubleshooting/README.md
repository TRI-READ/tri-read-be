# TRI:READ 트러블슈팅

운영 중 발견한 문제를 증상만 고치는 데서 끝내지 않고, 원인 분석부터 설계 변경, 검증과 운영 반영까지 분류별로 추적합니다.

## 분류

| 분류 | 범위 | 기록 |
| --- | --- | --- |
| 학습 정책·퀴즈 배정 | 콘텐츠 노출, 사용자 배정, 이월, 보너스 학습 | [학습 정책·퀴즈 배정](learning-policy.md) |
| 퀴즈 생성·AI | Gemini 호출, 생성 검증, 중복 검사, 호출 제한 | 사례 발생 시 `quiz-generation.md` 추가 |
| 데이터베이스 | 마이그레이션, 정합성, 성능, 백업·복원 | 사례 발생 시 `database.md` 추가 |
| 배포·운영 | CI/CD, OCI, 스모크 테스트, 모니터링 | 사례 발생 시 `deployment-operations.md` 추가 |
| 보안·인증 | 세션, 권한, 감사 로그, 취약점 대응 | 사례 발생 시 `security-authentication.md` 추가 |

하나의 문제가 여러 영역에 걸치면 사용자에게 나타난 문제와 해결 목표를 기준으로 주 분류를 정하고, 사례 본문에 전체 영향 범위를 표시합니다. 같은 내용을 여러 파일에 중복 기록하지 않습니다.

## 기록 양식

새 사례는 해당 분류 파일에 다음 순서로 추가합니다.

1. 분류, 영향 범위, 관련 이슈·커밋
2. 관찰된 증상과 사용자 영향
3. 재현 조건과 수집한 근거
4. 근본 원인
5. 검토한 대안과 선택 이유
6. DB, 백엔드, 프론트엔드 변경
7. 로컬 테스트와 CI 결과
8. 운영 배포와 사후 검증
9. 결과, 남은 위험, 후속 관찰 항목
10. 회고

## 기록 원칙

- 장애, 구조 개선, 성능 개선을 명확히 구분합니다.
- 추측보다 로그, 쿼리 결과, 테스트, 실행 링크 등 확인한 근거를 남깁니다.
- API 키, 비밀번호, 실제 환경변수 값과 사용자 개인정보는 기록하지 않습니다.
- 해결 코드만이 아니라 운영 반영 여부와 사후 검증 결과까지 남깁니다.
- 재발 시 기존 사례에 후속 내용을 추가하고, 원인이 다르면 새 사례로 분리합니다.
